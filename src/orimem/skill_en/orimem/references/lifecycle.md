# Automatic organizing and knowledge formation

Used for source distillation, stage organizing, formal knowledge merging and daily/weekly material selection. Archiving, actual reading, summarizing write-back, indexing and task use are each accepted separately. Semantic judgment is done by the current agent or the organizing task configured by the user; E5 only encodes; the background queue itself does not mean the model has read or summarized anything.

## Judging targets

First compare existing topics and projects, then read the necessary sources. Confirmed goals, constraints, results, obstacles, next steps and corrections go into the single project page; paused projects only have their records updated. Daily records cover actual progress, deliverables, decisions and changes; periodic reviews select milestones, reasons, cross-day trends, recurring problems and unresolved matters. Ordinary Q&A, small talk, unadopted suggestions and maintenance echoes skip body-text writes.

Methods that are reusable long term, have verifiable sources, clear applicability conditions, no important unresolved conflict, have been compared with existing knowledge, and can be explained on their own can be written or merged automatically into `30 Knowledge`. One high-quality source can be enough; historical cases not re-run this round do not automatically negate a general method, but specific old results can only be marked as historical reports. Explanations and inferences state their limitations; do not fake that the user has reviewed them.

Valuable candidates whose evidence or explanation is insufficient go into `00 Inbox/AI Drafts`, stating the existing basis, candidate conclusion, limits, points to verify and the evidence that would drive promotion. Re-judge when new support, conflicts or corrections arrive. Do not generate one article per session, or replace actual distillation with marking everything as to be verified.

## Source reading and registration

The unified MCP tool `lifecycle`(action, arguments) supports `discover`, `discover_pending`, `sources`, `read`, `ack`, `coverage`, `review`, `route`, `claim`, `finish_job` and `health`. Newly added actions may not yet be visible in the tool catalog cached by an old session; reloading in a new session is enough; do not start another indexing setup. arguments store only selected metadata or changes; do not copy chats wholesale.

`sources` returns current versions page by page; source keys are `archive:<session_id>` or `pending:<session_id>`. `read` takes `source_key, version (optional), start, max_chars`; chunks are at most 24000 characters, default 12000. It returns `ack_token,content_sha256,next_start`. After actually viewing the complete returned chunk, call `ack(token,content_sha256)`, then continue reading from `next_start`. Truncated tool output must be re-read; do not batch-acknowledge body text that has not entered the context. Offsets are Unicode character positions in the returned text, keeping original line breaks; the version hash binds the raw archive bytes or the canonical staged representation.

`review` requires `source_key,version,disposition,reason,comparison,claims`. The disposition is `merged/formal-knowledge/candidate/no-reusable-knowledge/conflict/needs-evidence`, and the source must really have been read in full. The comparison list uses existing in-vault paths that have been read. Each claim contains `text,path,heading(full heading array),strength,boundary,quote,start,end`; formal knowledge also has `promotion_reason`. Verification strength is one of `user-confirmed/historical-report/inference/verified-artifact`. The exact quote must support the claim; hash verification does not replace semantic verification.

Results with nothing reusable can register only metadata. When there are claims, first register them as pending write-back; close only after the shared writer has completed body text and indexing. The ledger is not a second copy of project status; claims and citations are used to link evidence and do not create a parallel project ledger.

## Daily/weekly material and recovery

`route` records `source_key,version,material_kind,quote,start,end,reason,event_time(nullable),primary_path(nullable),period_significance(nullable)`. Use it after actually reading the quote. Material kinds are `progress/decision/deliverable/obstacle/correction/experience/question/chatter/suggestion/maintenance`. Only progress-type material with a supported event date enters the daily queue; with periodic significance it also enters the weekly queue. Historical distillation from before automatic recording was enabled does not routinely create old daily reports; knowledge and projects are merged under current authorization. Leave unknown dates empty; the main body text of the same fact is written only once, and other entry points reference it.

Semantic distillation is registered as persistent tasks in the background and judged by an agent that gets a chance to execute; source saving and continuous projection are run independently by the program and do not wait for semantic distillation. `claim(kind,owner,lease_seconds)` takes a bounded lease; on exceptions, `finish_job(job_id,owner,error)` keeps bounded retries. Summarizing is complete only with full reading and a disposition; a periodic task is complete only with the corresponding writer receipt; index tasks are completed by hash and receipt reconciliation. Neither receipts nor task triggers prove source facts are correct.

Immediate, stage, manual periodic and enabled scheduled organizing (`daily_summary.enabled`) use the same judgment and write-back logic. Periodic plans provide `period.from_time,through,timezone_name,project_scope`, check real successful coverage of the full interval, and keep gaps pending. For an unfinished period, record only the actual range; do not claim stage coverage as a completed full week.

`project_scope` uses an explicit list of in-vault relative paths; a successful scoped scan cannot advance the global watermark or complete other projects. Each requested project needs coverage of the whole time interval; it cannot pass when the source scope is unknown or the project still has pending items. Weekly receipts distinguish in-scope period completion from full-week completion for all authorized sources; closing a single daily material receipt does not mean the whole day's scan is complete. Field details in [automatic-journaling.md](automatic-journaling.md).

Modification or loss of a current source sends its dependencies into the review queue; this only means pending re-judgment and cannot automatically decide new facts for the user. The persistent queue, stage health and read coverage can be checked with `health`. New-conversation hooks, recall quality evaluation and long-term unattended operation must each be really verified; do not infer completion from the existence of a queue.

## Target changes and review closure

`reconcile_targets` checks the actual heading paragraphs of recorded claims against current sources; unrelated paragraph edits keep still-valid claims, while target deletion or changed assertions enter review. A unique byte-identical indexed target can migrate the association; multiple identical copies are not guessed. Renamed historical evidence with a stable session_id can restore source binding without moving the actual file.

`dependency_reviews(limit,offset)` returns dependencies pending review with dependency_id, page by page. First actually read, compare, and complete full acks of required new sources, then evaluate the conclusion.

When replacement or withdrawal is needed, first modify the current assertion through the shared writer, read back, generate a receipt and index; keep necessary historical description. `resolve_review` parameters are `dependency_id,decision,reason,receipt_batch,target_path,heading,text,replacements`; decision is retained/replaced/withdrawn; replacements is a list of current dependency IDs (may be empty for withdrawal). The target sentence must be in the specified writer receipt and the current index; retention or replacement also requires a current supporting dependency that has been fully read and bound to a receipt. Replacement/withdrawal must not leave the old definite assertion in the original paragraph.

Closure keeps old dependencies, disposition reasons, replacement relations and original receipts; the processing time is not filled in as the invalidation time of unknown facts. Identical closures are idempotent; the block cannot be lifted by joining the queue, unrelated receipts or hand-edited metadata.

## Revising written-back assessments and promoting candidates

First use `assessment(source_key,version)` to get the original assessment and `assessment_sha256`, and actually compare new evidence with existing knowledge. Complete formal knowledge, correction paragraphs and the original candidate note through the shared writer, read back and index, then call `revise_assessment`. Parameters are `revision_id,source_key,version,expected_assessment_sha256,disposition,reason,comparison,claims,receipt_batch,retirements`.

New claims still require an exact contiguous source quote, full reading, verification boundaries and, for formal knowledge, promotion_reason; each target sentence must be verified by this receipt's exact checks and match the current body and index version. Removed old dependencies are provided item by item as `retirements[{dependency_id,path,heading,text}]`, bound to the handling note in this receipt; old definite assertions must move out of the original current heading paragraph and can be kept under an explicit historical heading. The original candidate can keep the promotion link and case-specific pending notes; do not delete sources or fabricate user review.

The original assessment, old dependencies, replacement relations and original receipts are all kept after revision; replaying the same revision ID with the same content is idempotent, with different content it is refused. When body text is written but indexing failed, keep the original assessment, fill in the index first, then close.

## Watching candidates for new evidence

After candidate body text and indexing are complete, use `register_candidate(source_key,version,candidate_path,topics,scope,reason,include_pending)` to register explicit topic terms, in-vault scope and the reason evidence is needed. `include_pending` defaults to false; staged sources must be chosen explicitly. A topic hit only produces a review signal; it does not prove facts or promote automatically. After a new version is discovered through archive index reconciliation or ordinary message staging, it enters the same persistent `candidate` queue; repeated versions are not queued again, and changes to the old version or source disappearance deactivate old tasks.

Stage or periodic organizing first looks at `candidate_tasks(limit,offset)`, then claims with `claim(kind="candidate",owner,lease_seconds)`. Fully read the corresponding evidence through the unified read/ack, exclude maintenance echoes, ordinary Q&A and circular references to the candidate itself, and make a semantic judgment. When evidence is still insufficient, call `candidate_decision(job_id,owner,decision="keep-candidate",reason,evidence_source_key,evidence_version)`, recording only the specific reason; do not create new body text. When promotion conditions are met, first complete the writer/index/revise_assessment above, then close with `decision="promoted"` and the actual `revision_id`. It cannot be completed without a current lease, full evidence reading or a promotion receipt.

Candidate watching only submits tasks; the current agent or user-configured organizing task performs the judgment, and the background does not call external models. Tests of new-evidence triggering and candidate retention cannot replace acceptance of long-term automatic operation.

## Consuming and closing Stop-stage tasks

Immediate, stage and daily/weekly organizing all first call `stage_tasks(scope,limit,offset)`, taking only short metadata under authorized project/course entries. Uncaptured sources stay awaiting-capture (`capture_now` can be used to capture them); staged or archived sources are bound to the current source_key/version; read coverage and summarizing results cannot be inferred from hook triggers.

Use `claim(kind="stage",owner,job_id,scope,lease_seconds)` to take a stage lease within the specified scope; uncaptured sources are not claimed and do not consume retry quota, and out-of-scope projects return no lease. Actually read and judge through the unified read/ack, compare, review, route flow. Body changes still go through the shared writer and indexing; when nothing is reusable, keep only the specific assessment reason. Finally call `stage_decision(job_id,owner,source_key,version,reason)`, which checks the current source version, full reading, final disposition, exact-paragraph writer receipts for all claims and the current index. Source changes, claims pending writing, expired leases, changed receipts or incomplete indexing all prevent closure; replay with the same content is idempotent. On failure use finish_job(error) to keep bounded retries; do not hand-edit task status.

stage_tasks is only a source readiness check, and stage_decision is only acceptance; semantic distillation is still performed by the current agent or an already configured user task, and no model is called within the short-lived hook. A hook definition that has not passed the client's native trust review does not run automatically; function/script tests do not mean the real new-conversation hook has fired.

## Immediate blocking and closure of explicit corrections

First actually read and distinguish whether it was wrong all along, changed from some point in time, or is still disputed. Vector proximity, latest time or the retraction of a single example do not constitute a correction relation. Use the same `lifecycle`, SQLite and writer; do not build a separate project status or fact ledger.

For new continuous sources, prefer selecting a specific message with `message_source(session_id,event_index,scope)`, then read/ack. Message versions are decoupled from other messages being appended; source edits still make old dependencies pending review; register only the messages actually used this time, and do not create semantic tasks in bulk for all messages. It returns upstream_truncated/completion/completeness; a full ack only proves the observed interface content was read in full and cannot restore upstream-truncated or unpublished content.

Once an explicit correction is identified, **register first, then update derived body text**: `register_correction(correction_id,kind,source_key,version,quote,start,end,targets,reason,scope,effective_at)`. kind is retraction/supersession/dispute; quote must be an exact contiguous range of the current source, and the source must have been fully acked. scope must include the correction source and all targets. targets use `{dependency_id,impact}`, where impact is assertion/example; for existing manual project paragraphs without dependencies use `{path,heading,claim,impact}`, bound to the current original version and heading, without forging old source dependencies. The ID cannot change content.

Handwritten targets whose source has actually been checked can explicitly add `origin:{source_key,version,quote,start,end}` and `expected_sha256`. origin must be within scope and fully read/acked, the current exact range quote must equal the claim, and the target's raw-byte SHA must be unchanged; this only establishes a source binding explicitly checked by the caller and does not create forged knowledge_dependencies. DB messages and old MD snapshots require separate versions/ranges; they cannot be presumed to be the same source by similarity or numeric numbering.

Registration immediately withdraws affected assertions from current retrieval; this is not restored even if the body has not yet been updated or indexing failed; other unaffected source paragraphs in the same chunk are fetched through exact safe ranges, and the general method is not withdrawn as a whole. Raw messages are not rewritten. A supersession's effective_at must have a source basis and timezone; leave unknown ones empty and do not fill in the processing time. A future rule does not replace the old rule before it explicitly takes effect.

Update the actually affected projects, knowledge, summaries and dated records through the same writer, save exact checks/receipts and index. Existing dependencies are still actually closed with resolve_review/revise_assessment; do not hand-edit metadata to lift the block. Claims for new rules carry a supported valid_from; old validity periods are closed only at an explicit effective time; a retraction does not disguise the old error as a previously correct rule.

Then call `finish_correction(correction_id,receipt_batch,scope,historical_sections,direct_resolutions)`. All dependencies must already be closed by the same receipt, with body and index hashes currently consistent. Retained old conclusions are listed section by section as `historical_sections[{path,heading,text}]` and exactly verified by the same receipt; a whole section containing other current claims cannot be swallowed as history. Manual body targets use `direct_resolutions[{dependency_id,path,heading,text,decision}]`, decision withdrawn/replaced; it still requires the old current assertion to leave the original section and the disposition note to enter the receipt, without creating forged dependencies.

Targets in the non-rewritable raw session history of `90 Archive/Conversations` use decision=`source-retained`, plus `proof_path,expected_sha256`. The source text must keep the byte SHA from registration time, the canonical message/archive source must have been fully read and the range bound to the current version; the same original assertion must have an explicit archive source-file gate. proof_path is within the same scope, and the same writer receipt verifies the disposition paragraph, original version and index; do not copy whole raw chats into a fact batch or close by deleting the original words. After closing, the original version/range continues to be withdrawn from current, historical keeps the original words with a correction annotation, and the independent general method can still be queried.

When all targets have already been closed as source-retained by the same receipt, a repeated finish allows the proof page to have unrelated content appended: it read-only checks the original receipt's fixed hash in state, the committed queue and the original plan's postimage/paragraphs, and that the current proof paragraph is still under the original heading, and that the current index/target bytes and all source versions/ranges still match. It returns idempotent=true, body_writes=0, resolution_writes=0, and adds no new closure rows. A first or not-fully-closed finish still requires the full proof page to match the receipt; an old receipt cannot bypass the current read-back of a new closure. Changed proof paragraphs, changed raw source/version, tampered receipts or queue, missing old closure rows or out-of-scope items are all refused.

A bound archive source file changing SHA also does not automatically lift a semantic correction: first locate the affected message section by the registered heading; current does not adopt the new version for now, and historical attaches corrected-origin-version-needs-review/not_current_basis; unrelated messages in different sections remain independently readable. When the original message heading has been renamed/removed and boundaries cannot be confirmed, conservatively wait for that file's review; do not guess identity from new position or similarity. This means the source version is pending review, not that the general method in the same file has been judged wrong; saving and projection keep running.

`corrections(scope,limit)` returns short disposition information. Partial multi-target writes, file locks, index failures or new source version changes all keep the block and recoverable tasks; local success does not complete all targets. Current and historical queries, future validity and source text are each accepted separately.
