# 自动记录的写回契约

仅在任务涉及自动记录、扫描补漏或修复写回时读取本文件。授权、来源范围及日周职责以库级 AGENTS.md 为准。

普通召回按 [retrieval.md](retrieval.md) 定向定位知识，历史缺口按 [history.md](history.md) 使用已经合并的正文与原生历史接口，不并行生成两份上下文。历史结果不能替代当前验证。相关时在交付中简短说明参考了哪条经验及适用边界，不为每次检索新建日志。

## 任务结束后的确认结果

先提取实际成果、决定、具体卡点和已确认下一步，比较原页。已有事实只补必要出处，不重复追加。项目状态与下一步仅在项目页维护，事件按配置时区的实际日期进入日记；证据明确、边界清楚且可长期复用的知识默认可以自动形成或合并，冲突或缺证据才留候选，详见 [lifecycle.md](lifecycle.md)。

自动写回统一经共享 writer，含项目、日记、候选、`30 知识` 和授权佐证：MCP `prepare_record`(plan) 返回差异和 prepared_sha256，`commit_record`(batch_id, prepared_sha256) 调用同一 writer；命令行等价入口为 `orimem write ...`。代理在既有授权内检查差异，无需每次另请用户确认。正文写前持久登记索引任务，成功收据后增量索引；索引失败单独补做，不能标整个链路完成。输入是本地 JSON 变更批次，不能把整段聊天或凭据放进去。读取旧文件时计算**原始字节** SHA-256，再生成保留既有字段、来源和用户段落的完整新内容。写回前检查增量差异，不能用省略号代替原文，也不利用此工具做未授权的删除或重构。

批次结构示例（仅示意，需要使用真实内容和时间）：

```json
{
  "batch_id": "task-unique-id",
  "through": "YYYY-MM-DDTHH:MM:SS+08:00",
  "scan_kind": "task",
  "scan_complete": false,
  "events": [],
  "changes": [
    {
      "path": "00 收件箱/AI 草稿/示例.md",
      "expected_sha256": null,
      "content": "---\ntype: example\ntags:\n  - 示例\n---\n\n# 示例\n\n## 结果\n\n示例，可删除。\n",
      "checks": [
        {"section": ["示例", "结果"], "text": "示例，可删除。", "events": []}
      ]
    }
  ]
}
```

- batch_id 在重试中保持不变。同一 ID 不得换内容；重新合并的版本使用新 ID。
- expected_sha256 是读取原页时的 64 位小写哈希；仅新文件用 null。
- content 是完整新笔记。checks 的 text 是要验收的真实完整句子，section 是唯一的完整父子标题地址，不只写 H2。
- events 只接受 session_id、ts、role 和 event_index 或 turn_id，可选 content_hash。app 回合时间由 Unix 秒转换为带时区时间，final_answer 使用完成回合时间，并保留 turn_id。来源仍放笔记文末。
- 使用 writer 状态的 seen 查询得到 fingerprint；checks.events 填对应指纹，每个新来源事件至少绑定一处事实。seen 输出中的 fingerprint 不能回塞到 events 的元数据项。
- 任务内已验收的产物也可 events=[]，在文末保留真实文件或当前请求依据；不要编造会话定位。源扫描补漏应使用真实事件元数据。
- pending 是 session_id、first_ts、reason 的列表；reason 只写简短缺口，不写正文。resolved_sessions 仅填写已确认处理完的会话 ID；其他待重试项自动保留。

writer 在同一 OS 锁内执行：检查全部原版本 → 库外备份 → 写入 → 回读并检查目标段落 → 保存收据 → 登记去重。收据绑定事件、笔记路径、标题、段落哈希和写后文件哈希。写后用 `health` 核对队列与索引状态。

写前解析 frontmatter，拒绝重复字段、无效 YAML、非列表 tags 和丢失原属性的合并。解析器不可用时保留批次，不自动安装依赖，也不跳过验收。

state.json 与 receipts 只存元数据/哈希。queue 中保存选定的变更内容，可能包含私人笔记，只在本机保留，不上传、Git 提交或作为未来任务指令。库外备份使用批次 ID，失败重试复用原副本，不重复创建。

## 每日扫描与每周汇总

定时日周整理由 `daily_summary.enabled` 控制：默认值 `"ask"` 表示向用户询问一次是否启用，未获同意前视为关闭；也可为 `true` 或 `false`。用 `config_get` 查看，用户同意后用 `config_set` 修改；启用后由 `orimem daily run` 执行。未启用时仍可按用户请求手动整理，规则相同。

项目范围的周期扫描在计划的 `period` 中提供 `from_time,through,timezone_name,project_scope`；`project_scope` 是非空库内相对路径列表，目录按路径边界覆盖其子路径，省略才表示全部授权普通来源。每日 `period` 起止必须与 `scan_from/through` 一致。完整的限定项目扫描只保存该范围的成功窗口，不推进全局扫描水位；周复盘逐个核对请求项目的整个时间区间，不能用项目A和B各半段凑成覆盖。范围已知的待补来源用 `pending[].project_scope` 记录；范围未知的待补来源保守阻断，重复失败保留未解决范围。

限定项目的整周完成与全部来源的整周完成分别记录；限定项目结果不会清除全局待补周。weekly-ready 核对可同时给出 from_time、through 与 project_scope（如 `"10 项目/项目页.md"`）。一次材料任务结案只表示该材料已有正确日期笔记和收据，不能据此声称整日扫描完整。

1. 用 health 和 window 查看待重试批次、窗口及 pending，再通过 `list_sessions`/`get_session_messages` 获取来源。失败批次每轮最多重试一次。
2. seen 筛选事件，按主题与已有笔记做事实比较；语义相同的重复报告复用已有段落作为 checks，不重复追加。指纹只处理消息重复，无法判断不同表述是否同一事实。来源发现后的候选复核任务按 [lifecycle.md](lifecycle.md) 的 candidate_tasks/claim/read/ack 流程处理；新证据不足时只保存判断理由，满足质量条件再通过同一 writer、索引和 revise_assessment 自动转正。
3. 日常批次使用 scan_kind=daily。仅完整分页、所需可读来源覆盖已核对且写入验收成功时设 scan_complete=true，并填真实 scan_from 和 through。截断、工具失败时用 false，保留 pending，不推进扫描水位。
4. 完整扫描无新事实时，可 changes=[]、events=[]，只登记扫描收据，不创建空白日记或“无更新”日志。不要把被忽略的寒暄等绑定到虚构事实。
5. 每日任务处理实际日期的项目与日记补漏，并按复用价值判断正式知识或候选；有阶段意义的材料登记为周期复盘素材，已即时写入的事实只引用，不重复追加。用 weekly-due 检查已结束但漏汇总的周，按实际区间 ready=true 才补汇总。既有周任务归纳日记、必要项目和定向补证，不例行再全量扫描聊天。
6. weekly-ready 按本次 from_time、through 和 timezone 检查成功扫描窗口并集、范围内待补来源及缺口。前置未满足时 defer-week 登记待补周，保留原复盘；后续覆盖缺口后可补汇总。未结束周期只记录实际范围，不能把阶段覆盖当作完整一周。固定钟点不作为处理完成条件。
7. 每周批次用 scan_kind=weekly、week=<周一日期>、scan_complete=false，并提供与覆盖检查一致的 period；检查对应每周文件及来源绑定。只写有依据的后续重点，不推断个人承诺。已汇总周出现后补事实时，写回再次标为待补，同一事项复用主要记录与已验收段落。

window、weekly-ready、defer-week、weekly-due 等状态查询与批次 retry、supersede（以已成功合并的新批次取代冲突批次）由同一 writer 提供，经 `orimem` 命令行调用；具体参数以其帮助输出为准。

并发冲突时重新读取原页，合并已确认的事实并生成新批次。不要自动回滚部分写入，避免覆盖后来修改；未登记事件仍可补漏。重试失败、来源不可读或冲突无法明确合并时报告具体缺口，不循环执行。共享锁只约束经同一 writer 的写入；Obsidian、同步软件或手工修改不参与锁，写前哈希与写后回读检测变化，不能宣称对任意外部写入提供绝对隔离。

最后区分脚本测试、真实写回和定时触发。扫描声明由执行任务核对，收据能证明指定内容进入笔记，不能替代事实审阅或证明全部聊天均已读取。

## 周期范围

weekly-ready 支持 from_time、through 和 timezone；提供本次实际要整理的起止范围，不依赖固定钟点。默认检查本周授权起点至调用时刻的真实覆盖；不能用只覆盖最后一个时刻的扫描冒充全区间。成功扫描窗口的并集有缺口或有范围内待补来源时拒绝完整结案。

weekly 写回计划提供 `period` 对象，字段为 `from_time,through,timezone_name,project_scope(可选)`，与检查参数保持一致；收据冻结这组范围。当前周尚未结束时按实读范围写阶段复盘，保留 recorded_through，不把阶段覆盖登记为全周结束。后补事实按原日期更新并使原周期待补。定时时间由用户自行配置，不擅自更改。

## 来源暂存与明确归档

普通消息由 `orimem capture`（`capture.enabled`，默认开启）先保存观察到的原文版本，由独立 projection 任务经同一 writer 持续更新 `90 归档/Codex佐证` 的稳定转录，不等待阶段或日周整理。投影批次可承载已授权的原文，events=[] 不冒充事实记录；checks 精确覆盖程序正文，source_projections 另绑定来源版本与收据。未变输入不写正文，冲突有限重试并保留源；不会写成草稿箱中的会话页。

日周扫描仍按消息真实时间读取 archived/pending 并比较已有事实。归纳结果通过同一 writer 写项目／日记；证据与边界充分的知识可创建或合并至 `30 知识`，缺证据或冲突保留候选。旧快照保留历史含义；连续转录是否完成看 projection 收据，而非兼容分页状态。本地内容不额外脱敏，凭据文件、第三方名单和来源授权边界仍有效。

## 已授权历史快照的引用维护

把旧索引双链迁移到 `90 归档/Codex佐证` 中精确消息标题属于显式维护，只对授权中逐项列名的既有笔记进行，不开放收件箱、资料或原始来源的整目录写入；普通自动写回/MCP 不开放此维护范围。

调用前须实际阅读对应原文，核对引用事实、角色、真实消息时间及源版本；数字编号和同ID映射仅产生候选。旧概要没有冻结的完整原文金标时，报告单条支持核验，不能宣称整会话全文等价。原有引用清单的分母保持；扩大扫描发现的条目分开登记，不能用新增范围替代原清单或隐藏未迁移引用。

维护只能将旧索引双链改为存在且唯一的消息标题，保留显示文字、历史正文和无关链接，并要求既有文件与原哈希。多事件分别链接到各自消息。删除、移动或正文整理仍服从当前授权和各自验收，不能借引用维护修改历史事实。

原编号在当前来源不存在时，必须实际读候选正文并核对原引用事实；选定不同编号还须显式提供当前编号、角色、真实时间、消息版本、来源文件SHA和选择依据。prepare 不按末条或近邻自动猜测；writer 保留原显示文字，只允许附加与原编号及实际目标标题一致的“（旧编号X→当前位置Y；原文支持核对）”。此标注表示经正文核对的引用迁移，不证明原数字身份或旧会话全文等价；缺失来源和未读名单仍留在原分母。

普通项目页若在同一单来源链接旁已明确列出多个事件，可逐条核对后将显示补充为各消息编号，正文、原事件列举与项目状态保持；这不扩展历史快照、收件箱或资料的显式维护范围。没有明确事件或多个来源并列时不据此猜测。

原会话级链接没有消息编号时，可在实际读原文后显式选定支持该引用用途的当前消息，使用与上述相同的角色/时间/版本/文件SHA绑定。old_event 保留 null，显示文字不变，目标为精确消息标题；不伪造旧编号，不把一条消息支持升级为整会话或全部事实等价。第三方名单等未读来源继续保留，不能按同一会话ID自动迁移。

## 旧整理稿的原位历史退役

原位退役只对明确列名的旧整理稿添加 `retrieval_basis: historical-only`、实际批次日期的 legacy_retired_at 和理由，原正文、双链、统计及全部既有YAML属性值必须不变。它不删除或移动历史，也不登记语义撤回。导航页维护仅限把旧整理依据链接改到既有归档索引的对应节，标签/正文/属性保留。普通 MCP/自动接口不暴露这类维护范围，不能借此开放原始资料或任意归档修改。

原位退役前实际核对独有内容与当前承接页，保持全部历史材料和原字节备份；完整会话等价未证实、截断、候选及未采纳建议仍保留。写回后逐文件原文/链接/属性/收据/索引和零写重放验收，另测 current 阻断及 historical 保留。物理删除、批量移动和目录重构仍先提交具体清单确认，不把原位退役当成已删除或已批准移动。

用户明确授权清理旧稿时，先承接独有正文与原属性、迁移引用、完成库外原字节备份及收据，再逐个按固定路径删除；手动留存页可放 `90 归档/旧文件`，正文不使用双链，只在索引保留入口。旧稿、旧编号和统计不改为当前事实，原始对话不改写。普通自动化不能据此按日期、孤立度或相似度搬动其它材料。留存转换比对既有整版，只改变双链语法、手动留存说明和明确索引属性；其它字段/内容与备份保留。

普通Markdown可显式设置 `orion_index: false` 供手动留存，索引对账会移除其 notes/chunks/edges 候选；原文仍在 Obsidian。源码与投影分开，不能用此字段声称已更改 canonical 原始对话的采集策略。writer 收据结案核对实际原文SHA、明确排除属性和索引缺席；不能把刻意排除当失败，或用无索引页完成 write-pending 正式知识主张。代码围栏中的示例/冻结属性双链不生成图关系；关系解析代际升级只对账派生边，不重算未变文本向量。

`90 归档/旧文件` 整个目录也排除Markdown检索，后续放入的手动旧稿即使尚未补 `orion_index` 属性也不会自动被索引；该目录与普通 `90 归档/Codex佐证` 来源分开。索引页仅为Obsidian手动入口，不扩展自动检索或归纳范围。

普通来源保存及 writer 投影由 `orimem capture` 负责，检索后端不重复采集。采集进程在运行只证明观察窗口内的保存，不能据此声称日周提炼已经完成，也不等于登录自启、异常重启、休眠与长期无人值守已验证。

批次仍走共享锁、库外备份、精确段落回读、收据与索引核验。失败补写使用原准备批次及同一维护范围；一般 retry 不能扩大范围。重验报告另存新文件，原收据与备份保留。
